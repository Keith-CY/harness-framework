# Harness Engineering：可执行落地文档

来源：OpenAI《Harness Engineering》，发布日期为 2026 年 2 月 11 日。  
原文链接：https://openai.com/index/harness-engineering/  
本文用途：把原文观点转成团队可执行的落地方案。

## 1. 目标

在现有工程团队中建立一套 `agent-first` 的工作方式，让 coding agent 能在明确边界内稳定完成更多任务，同时保持架构质量、可追溯性和可恢复性。

## 2. 适用范围

适用于已经有代码仓库、CI、基础测试能力的产品团队。  
如果团队还没有基本的自动化测试、环境启动脚本和文档习惯，应先补齐这些基础设施，再谈更高自主性。

## 3. 执行原则

### 原则一：先让系统可见，再让 agent 自主

不要先追求“全自动开发”。先确保 agent 看得清代码结构、运行状态、验证结果和失败原因。

### 原则二：文档必须是工作入口，而不是事后补充

凡是会反复影响 agent 决策的内容，都应写成文档并放在固定位置，例如架构边界、运行命令、约束条件、任务计划、验收标准。

### 原则三：把标准写进机制里

能自动检查的，不要只靠口头提醒。能用结构约束的，不要只靠 reviewer 记忆。

### 原则四：小步快跑，快速合并

把任务拆小，让每个改动易于验证、易于回滚、易于 review。吞吐量来自高频小变更，不来自超大 PR。

### 原则五：持续清理熵

在高产能模式下，删除、重构、对齐文档、收紧边界，是必须长期投入的工作，不是“有空再做”。

## 4. 目标状态

当这套方法跑顺后，团队应具备以下特征：

- 新任务可以在 10 分钟内被转成结构化上下文，交给 agent 开始执行。
- agent 可以独立启动项目、运行关键检查、定位常见错误并回传证据。
- 关键架构约束有文档说明，也有自动化约束。
- PR 默认小而频繁，review 关注风险与方向，而不是补全上下文。
- 文档和计划有明确生命周期，不会长期失真。

## 5. 仓库最低配置

建议在仓库中至少建立以下结构：

```text
docs/
  architecture/
  decisions/
  plans/
  runbooks/
AGENTS.md
README.md
```

各目录职责如下：

- `AGENTS.md`：agent 入口文档，告诉它应该先看什么、怎样启动、哪些规则必须遵守。
- `docs/architecture/`：模块边界、分层原则、核心数据流。
- `docs/decisions/`：关键设计决策及其原因。
- `docs/plans/`：正在进行与已完成任务的计划和结果。
- `docs/runbooks/`：启动、调试、发布、回滚、常见故障处理。

## 6. 4 周落地计划

### 第 1 周：建立事实来源

目标：让 agent 有稳定入口，不再依赖口头上下文。

执行项：

1. 创建或重写 `AGENTS.md`，至少包含以下内容：
   - 仓库启动方式
   - 测试命令
   - 常见目录说明
   - 代码修改约束
   - 提交与验证要求
2. 建立 `docs/architecture/`、`docs/plans/`、`docs/runbooks/`。
3. 为每个活跃模块补一页架构说明，写清职责、边界、依赖和禁止事项。
4. 为每个正在进行的较大任务创建计划文档，记录目标、步骤、风险和验收标准。

验收标准：

- 新加入的工程师或 agent 能在 30 分钟内独立启动项目。
- 关键模块不需要口头解释就能看懂基本边界。
- 每个在做任务都能找到对应计划文档。

### 第 2 周：提高运行与调试可见性

目标：让 agent 不只是“能改代码”，而是“能判断改动是否有效”。

执行项：

1. 统一本地启动命令，避免多套启动路径。
2. 为关键服务补齐健康检查、日志入口、测试数据装载方式。
3. 给前端或全栈项目补充可复现的调试路径，例如：
   - 本地开发地址
   - 登录或测试账号
   - 常见页面路径
   - 浏览器 DevTools 调试方法
4. 清理需要人工猜测的失败信息，把常见报错改成明确提示。
5. 为端到端或集成测试提供稳定的最小数据集。

验收标准：

- agent 能在不额外追问的情况下跑通关键验证链路。
- 失败日志能明确指出模块、原因或下一步排查方向。
- 调试路径文档化，不依赖资深成员口头说明。

### 第 3 周：把质量标准写进机制

目标：降低“agent 大量产出但质量不稳定”的风险。

执行项：

1. 把核心架构规则转成静态检查、lint 规则或测试。
2. 为关键目录增加 ownership 或 review 规则。
3. 明确 PR 必须附带的证据，例如测试结果、截图、日志、trace。
4. 收紧模块依赖，避免跨层调用和隐式耦合。
5. 建立任务模板与 PR 模板，要求写明目标、影响范围、风险和验证方式。

验收标准：

- 常见违规模式可以被自动阻止，而不是依赖 reviewer 发现。
- PR 的验证证据统一且可检查。
- 架构规则不再只存在于人脑中。

### 第 4 周：提高自主性并控制熵

目标：逐步提升 agent 独立完成任务的比例，同时防止仓库失控。

执行项：

1. 选择低风险任务让 agent 独立从计划到 PR 全流程完成。
2. 引入固定节奏的“清理任务”：
   - 删除无用代码
   - 合并重复实现
   - 归档过期计划
   - 修正文档漂移
3. 记录 agent 失败案例，归纳成文档、脚本或规则。
4. 每周复盘一次“哪些失败是 harness 问题，哪些才是模型问题”。
5. 把成功率高的任务类型沉淀为标准操作流程。

验收标准：

- 至少有一类任务可以稳定由 agent 独立完成。
- 每周都有明确的熵治理动作，而不是只新增不清理。
- agent 的失败原因可归类、可修复、可复用。

## 7. 标准作业流程

每个任务建议按下面流程执行：

### 步骤 1：定义任务

在 `docs/plans/` 中创建任务文档，至少写清：

- 目标
- 非目标
- 影响范围
- 约束条件
- 验收标准

### 步骤 2：提供上下文

把与任务直接相关的文档、目录、运行方式、已有决策链接给 agent。  
不要把大量无关上下文一起塞进去，重点是相关且最新。

### 步骤 3：要求小范围交付

单次只要求 agent 做一个清晰子任务，例如：

- 新增一个接口
- 重构一个模块
- 修复一个已定位问题
- 为一个现有功能补测试

避免让 agent 一次完成跨越多个上下文的大型抽象工程。

### 步骤 4：自动验证

要求 agent 在提交结果前自行运行必要检查，并返回证据：

- 单元测试
- 集成测试
- lint
- 类型检查
- 页面截图
- 关键日志

### 步骤 5：人类 review 聚焦高价值判断

review 重点检查：

- 方向是否正确
- 边界是否被破坏
- 复杂度是否不合理
- 文档是否同步更新
- 是否引入隐性耦合

不要把 review 时间浪费在能交给自动检查处理的问题上。

### 步骤 6：快速合并或快速修正

通过则尽快合并；不通过则指出最小修正集，避免长时间悬空的大 PR。

### 步骤 7：归档与回写

任务完成后：

- 更新相关文档
- 归档计划
- 记录异常点
- 如果踩了坑，把坑写入 runbook 或 AGENTS 入口

## 8. 文档模板

### 任务计划模板

```md
# 任务名称

## 目标

## 非目标

## 背景

## 影响范围

## 约束条件

## 执行步骤

## 验收标准

## 风险与回滚
```

### 架构说明模板

```md
# 模块名称

## 职责

## 输入与输出

## 依赖关系

## 禁止事项

## 常见修改路径

## 验证方式
```

### Runbook 模板

```md
# 场景名称

## 触发条件

## 排查步骤

## 常见原因

## 修复动作

## 验证方法
```

## 9. 指标体系

为了判断 harness 是否在变好，建议跟踪以下指标：

- PR 中位生命周期
- 单个 PR 平均变更规模
- agent 独立完成任务占比
- 回退或返工率
- 文档更新滞后率
- 测试失败中由环境问题导致的比例
- 同类问题重复出现次数

如果吞吐量升高，但返工率、环境故障率和文档漂移也同步升高，说明 harness 还不够成熟。

## 10. 角色分工建议

- `Harness owner`：负责 agent 工作入口、验证链路、文档结构和治理节奏。
- `Domain owner`：负责某个业务域的架构边界和质量标准。
- `Reviewer`：重点检查方向、风险和复杂度，而不是补上下文。
- `Agent operator`：负责任务分解、上下文提供和结果验收。

在小团队里，这些角色可以由同一批人兼任，但职责最好明确。

## 11. 常见误区

### 误区一：模型变强了，文档可以少写

实际情况通常相反。模型越强，团队越应该把高频约束显式化，这样模型能力才能变成稳定产能。

### 误区二：agent 产出快，就先合进去再说

如果没有验证和边界，速度只会把坏结构更快复制到全仓库。

### 误区三：只要给足提示词就够了

提示词只能部分补偿环境问题，不能替代清晰架构、稳定命令、可靠测试和最新文档。

### 误区四：review 可以省掉

高自主不等于无监督。review 的形式会变化，但最终责任不会消失。

## 12. 30 天后的交付物

如果按本文执行，一个团队在 30 天后至少应交付：

- 一份可作为 agent 工作入口的 `AGENTS.md`
- 一套清晰的 `docs/` 结构
- 关键模块的架构文档
- 至少一条稳定的验证链路
- 一套任务计划模板和 PR 验证要求
- 一份每周熵治理清单

## 13. 最终判断标准

不要用“agent 写了多少行代码”作为唯一成功指标。  
更重要的问题是：

- agent 是否更少迷路
- 人类是否更少重复解释
- PR 是否更小更快
- 质量标准是否更稳定
- 失败是否更容易恢复

如果这些指标在变好，就说明团队真正开始具备 `Harness Engineering` 能力。
